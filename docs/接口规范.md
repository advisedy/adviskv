# 接口规范

## 共同约定

### RPC返回值

所有的 RPC 返回里都要有 `BaseRsp`：

```proto
message BaseRsp {
    int32 code = 1;
    string msg = 2;
}
```

gRPC 本身能够正常返回，不代表业务请求一定成功，调用方还需要检查 `BaseRsp.code`。

### ID

- DatabaseID 由 Meta 创建，全局唯一并且自增；
- TableID 由 Meta 创建，全局唯一并且自增；
- ShardID 由 TableID + shard_index 构成，shard_index 是下标；
- ReplicaID 由 TableID + shard_index + replica_seq 构成，每个 ShardID 下的 replica_seq 从 0 开始，只自增；
- `operation_id` 用来标识一次建表、删表或者副本数调整操作；后台重试必须沿用原来的 `operation_id`，以保证幂等。

### replica_count 和 shard_count

- `shard_count` 只能在建表时设置，当前没有修改 shard 数的接口；
- `replica_count` 可以通过 `AlterTableReplicaCount` 修改；
- `replica_count` 可以为 0，`shard_count` 必须大于 0；
- Meta 的 DDL 接口是异步接口，返回成功只表示请求已经被接收；
- 最终状态需要通过对应的查询接口确认。

### route

- 关于 route 里面，不打算暴露出来CANDIDATE，只放进去 LEADER + FOLLOWER

## Meta

RPC 定义在 [`proto/meta.proto`](../proto/meta.proto) 中。DDL、路由、节点注册和心跳均由同一个 `MetaService` 提供。

### CreateDB

创建 Database。

请求：

- `db_name` 不能为空；
- `zone` 目前没有充分利用，定义上用于给用户做区域隔离。

成功：

- 返回新创建的 `db_id`；
- `db_id` 删除后不会重新分配。

失败：

- 参数不合法：`INVALID_ARGUMENT`；
- 同名 Database 已经存在：`ALREADY_EXIST`。

### DropDB

删除 Database。

请求：

- `db_name` 不能为空；
- Database 下不能还有未进入 `DELETED` 状态的 Table。

成功：

- 返回被删除的 `db_id`；
- `db_id` 不会重新分配。

失败：

- 参数不合法：`INVALID_ARGUMENT`；
- Database 不存在：`DB_NOT_FOUND`；
- Database 下还有未删除的 Table：`INVALID_ARGUMENT`。

### CreateTable

创建 Table。

这个接口是异步接口。

请求：

- `db_name`、`table_name` 不能为空；
- `shard_count > 0`；
- `replica_count >= 0`；
- `engine_type` 当前为 `MAP`；
- `resource_pool` 目前允许空

成功：

- 返回 `table_id`、`phase` 和 `operation_id`；
- 返回 `OK` 只表示 Meta 接收了请求，不表示 Table 已经创建完成；
- 后续通过 `GetTable` 查询最终状态；
- `replica_count=0` 时，Table 可以进入 `READY`，但没有 route，不能进行 KV 读写。

失败：

- Database 不存在：`DB_NOT_FOUND`；
- 同名 Table 已经存在：`ALREADY_EXIST`；
- 参数不合法：`INVALID_ARGUMENT`。

### DropTable

删除 Table。

这个接口是异步接口。

请求：

- `db_name`、`table_name` 不能为空；
- Table 未进入 `DELETED` 时都可以请求删除；
- Table 已经是 `DELETING` 时，重复请求直接返回成功。

成功：

- 返回 `table_id`、`phase` 和 `operation_id`；
- 返回成功时，Table 通常只是进入 `DELETING`；
- 后续通过 `GetTable` 查询是否已经进入 `DELETED`。

失败：

- Database 不存在：`DB_NOT_FOUND`；
- Table 不存在：`TABLE_NOT_FOUND`；
- 参数不合法：`INVALID_ARGUMENT`。

### AlterTableReplicaCount

修改 Table 的副本数，不修改 shard 数。

这个接口是异步接口。

请求：

- `db_name`、`table_name` 不能为空；
- `replica_count >= 0`；
- 当前 Table 必须是 `READY`；如果 Table 已经是 `RESIZING`，只有目标副本数相同的重试请求会被接受。

成功：

- Table 是 `READY` 且新旧副本数相同时，直接返回成功，不产生新的操作；
- Table 是 `RESIZING` 且目标副本数相同时，沿用原来的 `operation_id`，直接返回成功；
- 副本数发生变化时，返回新的 `operation_id`，Table 状态变成 `RESIZING`；
- 后续通过 `GetTable` 查询最终状态。

失败：

- Database 不存在：`DB_NOT_FOUND`；
- Table 不存在：`TABLE_NOT_FOUND`；
- Table 正在进行另一种副本数调整：`INVALID_ARGUMENT`；
- Table 不是 `NORMAL` 或参数不合法：`INVALID_ARGUMENT`。

### GetTable

查询 Meta 中的 Table 信息和状态。

请求时填写下面的一组参数：

- `db_name + table_name`；
- 或者 `table_id`，并把 `use_table_id` 设置为 true。

成功：

- 返回 `db_id`、`table_id`、`shard_count`、`replica_count`；
- 返回 `phase`、`operation_id`、`last_error_msg` 和 `engine_type`；
- 按 `table_id` 查询时，历史上已经进入 `DELETED` 的 Table 仍可能返回成功和 `DELETED` 状态；
- 按名称查询时，已经删除的 Table 不再出现在名称索引中。

失败：

- Database 不存在：`DB_NOT_FOUND`；
- Table 不存在：`TABLE_NOT_FOUND`；
- 查询参数没有正确填写：`INVALID_ARGUMENT`。

### GetTableRoutes

查询整张 Table 的 route，SDK 用它刷新路由缓存。

请求：

- `db_name`、`table_name` 不能为空。
- `include_unavailable` 默认 `false`；管理查询可设为 `true`，查看暂时不可用的 shard。

成功：

- 返回 `table_id`、`shard_count` 和每个 shard 的 route；
- 每条 route 带有持久化的 `hash_range{start,end}`，左闭右开，覆盖固定 bucket 空间 `[0,65536)`；范围指 hash(key) 映射后的 bucket，不是原始 key 的字典序；
- 默认所有 shard 都有可写 Leader 后才返回成功；`include_unavailable=true` 时允许空副本列表；

失败：

- Table 不存在：`TABLE_NOT_FOUND`
- 默认模式下任意 shard 的 route 没准备好：`ROUTE_NOT_FOUND`。


### RegisterNode

Storage 启动时向 Meta 注册节点。

请求需要填写 `node_id`、IP、端口、`resource_pool` 和 `dc`。成功后节点可以发送 `Heartbeat`。

- 参数不合法：`INVALID_ARGUMENT`。

### Heartbeat

Storage 定期上报节点和 Replica 信息，Meta 返回期望执行的操作。

上报内容包括 ReplicaID、Raft role、Storage 状态、term 和 member type；Leader 还需要上报完整的 Raft membership。

返回的操作包括：

- `PRESENT`；
- `ABSENT`；
- `ADD_MEMBER`；
- `REMOVE_MEMBER`。

没有先调用 `RegisterNode` 或参数不合法时，Heartbeat 返回错误。

## Storage

RPC 定义在 [`proto/storage.proto`](../proto/storage.proto) 中。

### Put

写入一个 KV。请求携带 `ReplicaID`、`key`、`value`，自动生成 `request_id`，并发送到对应 shard 的 Leader。

`request_id` 是一次业务写请求的幂等 ID。重复提交只执行一次，不会计入 Raft Log 等内容。

成功：

- Leader 将 Put 写入 Raft log；
- 日志满足 Raft commit 条件后返回 `OK`。

失败：

- Replica 不存在：`REPLICA_NOT_FOUND`；
- 当前 Replica 不是 Leader：`NOT_LEADER`；
- Replica 正在恢复：`IS_RECOVERING`；
- Replica 本地已故障：`IS_FAULTED`；
- Replica 尚未就绪：`NOT_INIT`；
- 等待提交超时：`NOT_YET_COMMIT`（可能进入了Raft Log，但是还没有确认多数派提交），不能确定请求最终是否生效；SDK会重试，最终重试失败会返回 `UNKNOWN` 


### Get

读取一个 KV。请求携带 `ReplicaID` 和 `key`，当前版本只从 Leader 读取。

成功返回 `value`。

失败：

- Replica 不存在：`REPLICA_NOT_FOUND`；
- 当前 Replica 不是 Leader：`NOT_LEADER`；
- Replica 正在恢复：`IS_RECOVERING`；
- Replica 本地已故障：`IS_FAULTED`；
- Replica 尚未就绪：`NOT_INIT`；
- key 不存在：`KEY_NOT_FOUND`；
- ReadIndex 屏障尚未准备好：`READ_INDEX_NOT_READY`；SDK 重试预算耗尽后返回 `SDK_TRY_AGAIN`；
- 当前 Leader 无法用多数派确认自己的身份：`NOT_LEADER`。

### Delete

删除一个 KV。请求携带 `ReplicaID`、`key` 和 `request_id`，并发送到对应 shard 的 Leader。

- 删除日志提交后返回 `OK`；
- 删除不存在的 key 也可以返回成功；
- Replica 不存在：`REPLICA_NOT_FOUND`；
- 当前 Replica 不是 Leader：`NOT_LEADER`；
- Replica 正在恢复：`IS_RECOVERING`；
- Replica 本地已故障：`IS_FAULTED`；
- Replica 尚未就绪：`NOT_INIT`；
- 等待提交超时：`NOT_YET_COMMIT`，不能确定请求最终是否生效。


### Replica 管理接口

包括 `CreateReplica`、`DeleteReplica` 和 `GetReplicaInfo`，当前受 `enable_test_api` 控制，主要用于测试和调试。

- `CreateReplica` 需要 `ReplicaID`、`engine_type` 和初始成员列表；
- `DeleteReplica` 需要 `ReplicaID`；
- `GetReplicaInfo` 找不到 Replica 时返回 `OK`，但 `exists=false`；
- 正常运行时，这些接口不是 SDK 的数据请求接口。

### Raft RPC

Replica 之间的 Raft 通信

- `RequestVote`；
- `AppendEntries`；
- `InstallSnapshot`。

目标 Replica 不存在时返回 `REPLICA_NOT_FOUND`。

### TestGetReplicaState

这个接口只用于测试和调试，当前受 `enable_test_api` 控制。成功时返回 Replica 的 role、Storage 状态、current term、commit index、last applied、snapshot index 和 snapshot term。

- 请求使用 `table_id + shard_id`，不是完整的 `ReplicaID`；
- `enable_test_api=false` 时返回 `ERROR`；
- 找不到对应 Shard 的 Replica 时返回 `exists=false + ERROR`，不是成功响应。

## SDK

SDK 的实现入口是 [`KVClient`](../src/sdk/client.h)，一个 `KVClient` 实例绑定一个 `db_name + table_name`。

```cpp
Status put(const Key& key, const Value& value);
Status put(const Key& key, const Value& value, const std::string& request_id);
Status get(const Key& key, Value* value);
Status del(const Key& key);
Status del(const Key& key, const std::string& request_id);
```

SDK 的行为：

- 根据 key 和 `shard_count` 计算 shard；
- 从 Meta 获取 route，并将请求发送到对应 shard 的 Leader；
- route 不存在时返回 `ROUTE_NOT_FOUND`；
- 普通 `put/del` 自动生成 `request_id`；显式传入 ID 的调用方可以在进程重启后继续重试同一个逻辑请求；
- Storage 返回 `NOT_LEADER`、`REPLICA_NOT_FOUND`、`ROUTE_NOT_FOUND`、`IS_RECOVERING`、`IS_FAULTED` 或 `NOT_INIT` 时，SDK 刷新 route 后重试；刷新次数受 `route_max_retries` 限制，冷启动时因缓存未命中触发的首次刷新不计入该次数；
- Storage 返回可重试错误时，使用同一个 `request_id` 进行重试；重试次数耗尽且结果仍无法确认时才返回 `UNKNOWN`；
- Storage Get 返回可重试错误时，会进行重试，重试预算耗尽后返回 `SDK_TRY_AGAIN`；
- Put/Delete 受 `write_timeout_ms` 和最大重试次数限制，Get 受 `read_timeout_ms` 和最大重试次数限制；每次 Meta/Storage 调用使用 `rpc_timeout_ms` 作为单次 RPC 上限。重试初始等待时间由 `retry_delay_ms` 指定，之后每次翻倍，并受请求总耗时限制。

- `UNKNOWN` 只表示写请求的最终结果还不能确定，不表示操作一定失败。
- `SDK_TRY_AGAIN` 表示本次读请求没有完成，调用方可以发起一次新的 Get。

SDK 配置包括：

- `db_name`；
- `table_name`；
- Meta 地址和端口；
- 单次 RPC timeout；
- 一次写请求的总耗时上限；
- 一次读请求的总耗时上限；
- Put、Get、Delete 的最大重试次数（不包含第一次请求）；
- 路由表刷新的最大重试次数；
- 重试初始等待时间（之后是翻倍等待）；
- route 后台刷新间隔。
